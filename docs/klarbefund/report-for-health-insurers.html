1. What Klarbefund does

A person photographs a laboratory report or opens the laboratory's PDF. The app reads it on the device, codes every row with LOINC and UCUM, keeps the printed reference range, shows trends across reports, and exports the record as FHIR R4, OMOP CDM, JSON or PDF. Values read from a photograph stay preliminary until the person checks them; only a laboratory's own PDF text layer yields final. With consent the app writes the person's record into their own account on the EHDS demo hub, and weekly means from Apple Health beside it. Nothing leaves the phone otherwise.

2. Accuracy

The measure compares an extraction with a hand-checked truth, field by field: value, unit, code, reference range and date. The number that matters clinically is silent errors, rows the app showed as a value and got wrong. The benchmark asserts zero under every condition.

6. Integration paths

  1. White-label app. The app as it is, renamed and signed by the insurer, with the insurer as operator: privacy notice, DPIA, processor agreement for the hosted explanation service (Azure OpenAI, EU data zone, by default), and the Apple account. The code stays open source.
  2. Components into an existing ePA or EHR app. The shared Swift package (scanning, the 1751-coding dictionary, provenance, FHIR and OMOP writers, consents) has no third-party dependency and is covered by 419 tests; it drops into an existing iOS app. The same dictionary exists in TypeScript for a server-side path.
  3. Hub-side only. An insurer's platform reads the record as FHIR R4 from the hub's API, or runs the ePA ingest tool against PDFs it already holds, without the app.

In every path the insurer owns the data protection roles; the project supplies the templates and the evidence.
