FOUR AREAS TO PLAN

Where the migration work is

1 · Data model

Participant contexts, dataspace profiles, a new data plane record, stricter policies and credentials, no in-place database upgrade.

2 · APIs and security

Management API v5, IdentityHub v1, OAuth scopes instead of roles, renamed settings.

3 · Data plane

None in the box. Ours were replaced, not migrated: siglet for pull, and a data plane on the DataPlane SDK for push and Kafka (local, in progress).

4 · Signalling

Data Plane Signaling between control plane and data plane, on both the provider's and the consumer's side.

1 · DATA MODEL

A participant is now a context, not a connector

0.x 1.0 WHAT TO DO
Tenant One connector per participant Participant contexts in one control plane; the token's sub is the context id Provision a context per participant; scope every management call to it
Context state Active is 300 Active is 200 Rewrite any SQL fixup written for 0.x
Dataspace profile Implicit Each context linked to http-dsp-profile-2025-1, or a catalogue request answers 400 "No profile" PUT /v5/participants/{id}/profiles at onboarding
Data plane record transferTypes profiles (RC6, #6196), new DataPlaneInstance key (#6143), one per context Register on the consumer's side too, or the transfer ends "No dataplane found"
Persistence In-place schema migrations No upgrade path between RCs; negotiations and transfers run as tasks on NATS JetStream Fresh database set per release; keep the old one and its Vault keys for rollback
[2:30] The state code and the profile link cost us the most time, because neither fails loudly. The NATS streams are created in memory at startup only; we added a liveness check (ADR-084) after EDC declined it upstream.

1 · DATA MODEL, CONTINUED

Policies and credentials are validated, not trusted

0.x 1.0 WHAT TO DO
Policy terms Unknown actions and left operands pass Refused unless bound to a scope. 23 actions and 8 operands of ours Declare your vocabulary in an extension; enforce what matters with a policy function
Agreement A partial offer policy was accepted TERMINATED: "Policy in the contract agreement is not equal to the one in the contract offer" Send the offer's whole policy when you negotiate
Right operand {"@id": ...} accepted Rejected (RC6, #6164) Use plain values in seeds and offers
Credential format The holder asks for a format The issuer's profile decides, e.g. VC2_0_JOSE (IdentityHub #1248) Align credential requests with the issuer; watch for issuance stuck in state 150
Verification JWT and Linked Data JWT only by default (RC8, #6242); unknown credentialStatus refused (#6243) Add decentralized-claims-ldp if a partner issues Linked Data credentials
[2:00] Stricter validation exposes every demo shortcut. Note that EDC never enforced our EHDS constraints, on 0.18 or 1.0: declared is not enforced. We enforce one term in the connector today (ADR-090); the rest still in the hub.

2 · APIs AND SECURITY

Every API changes version, and roles become scopes

0.x 1.0 WHAT TO DO
Management API v3, v4, v5beta v5 only; old paths answer 404. Unscoped endpoints answer 403 (#6139) We changed 315 references: UI, tests, mocks, API collection, seeds, scripts
Identity APIs IdentityHub and IssuerService v1alpha v1 Same sweep; include provisioning agents
Authorization A role claim OAuth scopes: management-api:admin, identity-api:admin, issuer-admin-api:write Rework the IdP clients. A mistake locks clients out or makes them all admins
Settings edc.iam.trusted-issuer.* read with a warning Only edc.iam.trustedissuer.*; otherwise every DSP request is a bare 401 Diff each app's effective settings against a known-good stack before seeding
Protocol DSP per connector DSP 2025-1 through the context's profile; unverifiable requests answer 503, not 401 (#6193) Run the DSP TCK against your control plane on every release
[2:30] The security model is the riskiest part. A refused DCP token is a bare 401: diagnose by configuration, not by log.

2 · APIs, CONTINUED: THE CATALOGUE

The catalogue moved into the Connector

0.x 1.0 WHAT TO DO
Where it lives FederatedCatalog, its own repository and crawler In the Connector. FederatedCatalog archived 2026-03-19; the multi-participant cache came after RC5 (Connector #6199) Give your crawler a new source of truth. Ours still reads mock DSP endpoints (#929, open)

[2:00] The shape of a DSP catalogue did not change much; where it comes from did. For a health dataspace the DCAT in DSP is too thin, so the HealthDCAT-AP record travels as data under its own contract. Tractus-X has the same question with its own semantic models.

ONBOARDING WITH CFM

CFM puts a participant onto a 1.0 control plane in one call

WHAT IT IS

Connector Fabric Manager

A tenant manager, a provision manager and agents for the control plane, IdentityHub, jwtlet, registration, onboarding and siglet.

Upstream's provisioning layer for EDC 1.0: JAD and the core-platform-distribution chart deploy it beside the connector.

WHAT IT DOES FOR US

Deploy and dispose

One call to the tenant manager creates the participant context, its identity and keys, its credentials and its siglet; one call removes them.

Compose: 12 of 12 (deploy, DSP catalogue, dispose). Azure since 2026-11-20: 10 passed, 0 failed.

WHY A FORK

v0.0.9-mvhd.2

The agents get tokens by exchanging a Kubernetes service-account token. Keycloak answers 400 "supports access tokens only".

Six patch branches on the release tag, each with Go tests, one of them client credentials for the exchange. Upstream pull requests wait for the contributor agreement.

If you run outside Kubernetes: test CFM's token exchange against your identity provider before anything else.

ADR-085 · ADR-088 · runbook: the CFM fork · #1043 · ma3u/cfm

[2:00] Multi-tenancy means someone has to create the tenants. On 0.x that was a connector deployment per participant; on 1.0 it is a participant context, and CFM is how upstream creates them. Its model is not tied to Kubernetes; its token exchange is.

3 · DATA PLANE

Replaced, not migrated

0.18

Two Java data planes

One launcher per dataset family: FHIR and OMOP. Both proxied the hub's API.

The consumer read endpoint and token from a database column.

Deleted on 2026-11-09.

1.0 · OURS

siglet plus one endpoint

siglet answers Data Plane Signaling and issues a short-lived access token. It serves no data.

One endpoint in our Neo4j proxy, about 150 lines, checks that token against siglet's keys and serves the dataset it names.

The consumer asks its own siglet for {endpoint, token}.

1.0 · WHEN YOU NEED MORE

Your own, on the DataPlane SDK

siglet is pull only: one transfer type, HttpData-PULL.

Push, streaming or a large file extract needs a real data plane that speaks DPS.

Prove it with the DPS TCK. Ours is on the next slides, still local.

Decision: ADR-078, decision 5 · How it runs: stack and environment

[2:00] Do not port your 0.x data plane line by line. Ask what it really did. Ours only proxied an API behind a token; siglet does the token part and a tiny endpoint does the rest.

4 · SIGNALLING

An HttpData-PULL transfer on 1.0, step by step

  • Both sides need a data plane registered for the context, or the transfer ends "No dataplane found".
  • Token renewal after an hour needs a per-participant signing-key mapping in siglet that nothing creates by default.
  • siglet 0.1.6 refuses a plain http refresh endpoint unless [token.refresh_endpoint_policy] allow_http = true.
  • The registration body changed in RC6 (profiles). Write both forms during an overlap so a rollback still works.
[3:00] Walk the six arrows. The consumer app never reads the control plane's database any more: it asks its own siglet. That is the change most integrations will feel.

WHICH SIGLETS RUN TODAY

Three data planes: pull, push into an SPE, a Kafka stream

1 · PULLAZURE

siglet 0.1.6

Pinned by digest, on Compose and Azure. Each participant context registers its own siglet-<context> for HttpData-PULL; the CFM siglet agent sets it up at onboarding.

The data comes from /dataspace/data in our Neo4j proxy, which checks siglet's token: FHIR R4, OMOP CDM 5.4, HealthDCAT-AP.

2 · PUSHLOCAL

mvhd-dataplane

Our data plane on the DataPlane SDK 1.2.1 (the version RC8 pins), registered beside siglet as mvhd-dp-<context>.

HttpData-PUSH, HttpStream-PUSH, HttpFile-PUSH into the inbox of an attested secure processing environment: all three COMPLETED on Compose.

3 · STREAMLOCAL

the same, over Kafka

Kafka-PUSH and Kafka-PULL, one topic per transfer.

One hour of ECG: 121 of 121 records both ways, the same SHA-256. The 24-hour run stopped on the proxy's rate limit.

Honest status: siglet does push only as a token service: with tokenSource = "client" the consumer's siglet issues the token for its own inbox, and the provider's application does the pushing. Kafka has no DPS transfer profile yet. So 2 and 3 are a data plane of ours on the DataPlane SDK, the way EDC's own end-to-end tests run push and streaming (an ADR, proposed, still local). Not committed, not on Azure; token renewal (#888) not yet proven.

jad/siglet-edc1.toml · routes/dataspace.ts · cfm/sigletagent.dotenv · dataplane-sdk-java v1.2.1

[2:00] Answer to "which siglets": one siglet deployment for pull, used by every participant context, on Azure. siglet can take part in an HttpData-PUSH, but only by issuing the token for the consumer's inbox; it moves no bytes, and it has no Kafka. EDC's own e2e tests run Finite and NonFinite push and pull against a data plane on the DataPlane SDK, and so do we: registered beside siglet, the control plane picks by transfer type. Our transfer type names are not the DPS profile URLs yet, and Kafka has no registered profile. Say clearly that 2 and 3 run on my laptop's compose stack today.

PUSH INTO A SECURE PROCESSING ENVIRONMENTLOCAL

No push into a workspace that is not attested

CONSUMER DATA PLANE

1 · prepare

Asks the SPE for an inbox for this flow. Refused unless the workspace's latest attestation passed. Answer: address, one-time token, attestation record.
PROVIDER DATA PLANE

2 · start

Checks the record against its floor: simulated < node < workload. Below it: TERMINATED, with the reason.
PROVIDER DATA PLANE

3 · read

Waits for the consumer's "started", then reads the dataset page by page with a token it signs. Pseudonymised at the source.
SPE INBOX

4 · receive

Compares the SHA-256 it computed with the sender's. Refuses a difference, and any Patient that still carries a name, address, identifier or full birth date.
AUDIT CHAIN

5 · record

Opened, started, received, refused: each on the hash-chained spe chain. Local: 45 events, intact.
KEYS

Control plane to data plane: a Keycloak token of one client, checked. Back: an RS256 token the data plane signs, sub its id, checked against its JWKS. The inbox token never leaves the consumer's side.

HONEST LIMITS

Local floor simulated: no confidential hardware on a laptop; Azure would use workload. The provider trusts the record the hub relays; verifying Trustee's token itself is the next step.

[2:30] EHDS Article 73: data for secondary use ends in a secure processing environment. With pull, our hub's web server held the data on the way. With push, the holder's data plane writes straight into the workspace's inbox, and only after it has seen the attestation. Everything here runs on the compose stack today, not on Azure.

EXAMPLE: A LONG-TERM ECG OVER KAFKALOCAL

A Kafka stream is one transfer request away

{
  "@type": "TransferRequest",
  "contractId": "<agreement>",
  "assetId": "ecg-holter-hour",
  "transferType": "Kafka-PUSH",
  "dataplaneMetadata": {
    "@type": "DataplaneMetadata",
    "properties": { "speId": "SPE-1" }
  }
}

POST /v5/participants/{ctx}/transferprocesses. dataplaneMetadata reaches the consumer's data plane in prepare and names the workspace.

  • Test data: a synthetic Holter ECG, two leads at 250 Hz, one FHIR Observation with sampled data per 30 s.
  • One topic per transfer, one partition, so the order of the recording is the order on the topic.
  • Every record acknowledged, none twice; a last record carries the count and the SHA-256.
  • The consumer commits an offset only after the inbox stored the batch, and closes the inbox only when count and hash agree.

Both 1-hour runs end with the same SHA-256 (9b7021d4a2e2…). The broker on Compose is plain text; one shared between organisations needs TLS, SASL and an ACL per topic.

[2:00] The point for Tractus-X: streaming is a transfer type, not a side channel. The contract, the policy and the audit stay the same; only the data plane differs. Clicks: the request, the list, the results, then the lane: records run over the topic and the inbox counts to 121, then the END record arrives and count and hash agree. The 24-hour run found a real limit: our proxy's query rate limit counts the paging. That is the next fix.

WHAT WE WOULD HAND TO ANYONE MIGRATING

Eight learnings

  • Old settings are the risk, not new ones. Diff effective config before you seed.
  • A refused DCP token is a bare 401. Diagnose by configuration, not by log.
  • Fresh databases per release. Keep the old set and its Vault keys for rollback.
  • Fresh Vault aliases for generated keys. An existing alias gives a masked 500.
  • A stalled issuance is a state number. 100: the issuer cannot sign. 150: the holder refused.
  • Check your shadow jars. An old jakarta.json broke numeric policy values at runtime.
  • Gate from empty volumes, every suite, every tenant. Only the second data space found a break.
  • The release notes do not find the breaks; the gate does. This migration: 29 findings.
